## ADR-007 en ADR-008: wél formeel vastgesteld — en in directe tegenspraak met "voorkeur Azure DevOps"

- **Punt:** CI/CD wordt standaard gehost in een **eigen GitHub-organisatie** van Bitmetric (niet Azure DevOps), met één repo per klant en een herbruikbare workflow via versietag. Azure DevOps wordt expliciet overwogen en **verworpen**: "Gelijkwaardig alternatief... Verworpen op werkcomfort, niet op techniek. Heroverwegen als de GitHub-beperkingen gaan knellen."
  **Bron:** `FMD/docs/adr/007-cicd-in-eigen-github-organisatie.md` (ADR-007, Accepted). **Status:** vastgesteld — dit **conflicteert direct** met de `Promp.txt`-claim "voorkeur voor Azure DevOps (approval gates, Key Vault-gekoppelde variable groups)".
- **Punt:** GitHub Free heeft geen environment-secrets/approvals/branch-protection voor private repo's (pas vanaf Pro/Team/Enterprise); praktische vervanging: de Prod-deploy draait als `workflow_dispatch` met de tag als input — "geen approval-registratie, wel een bewuste handeling." Plan: starten op Free, overstappen naar Team bij ≥2 klanten.
  **Bron:** `FMD/docs/adr/007-cicd-in-eigen-github-organisatie.md`, sectie "Beperkingen van de gratis laag". **Status:** vastgesteld.
- **Punt:** Eén repository per klant, met een map per workspace (niet één repo per workspace); Fabric's git-koppeling is 1-op-1 tussen workspace en *branch*, niet tussen workspace en *repository*. Deploy-scripts/migraties/docs staan bewust buiten `workspaces/`.
  **Bron:** `FMD/docs/adr/008-repo-en-mapstructuur.md` (ADR-008, Accepted). **Status:** vastgesteld.
  **Update (2026-09-30, geautomatiseerde repo-watch): ADR-008 is per 2026-09-29 Superseded by ADR-011.** Reden: de ontwikkelflow is end-to-end getest in de klantsimulatie FMD_TRIAL (`testplan-devflow.md`, F0 t/m F8), en "één repo per klant, map per workspace" bleek daar drie problemen te geven. Na een *branch out* wijzen alle verwijzingen tussen workspaces nog naar Dev (het model naar Gold (D), het rapport naar SEMANTIC (D), de shortcuts naar Silver (D)), zodat een notebook in een developer-workspace in de gedeelde Gold kan schrijven. Een value set per developer lekte via `dev` naar Test en Prod, en een domeinwissel faalde als de actieve value set in de nieuwe branch ontbrak (`DependencyNotFound`). En items met dezelfde naam in verschillende domeinen (`LH_GOLD_LAYER`, `NB_GOLD_SHORTCUTS`, `VAR_GOLD_*`) hebben per domein een eigen logical ID, waardoor koppelen aan een ander domein via de API faalt met `LogicalIdConflictDetected`.
  ADR-011 (Accepted, `docs/adr/011-ontwikkelflow-repo-per-workspace.md`) kiest nu **één repository per workspace** (bijvoorbeeld `<KLANT>_FINANCE_CODE`, `<KLANT>_FINANCE_DATA`), plus generieke developer-workspaces per developer (`DEV_<NAAM>_<prefix>_{DATA,CODE,SEMANTIC,REPORTING}` en `DEV_<NAAM>_<prefix>_INTEGRATION_{DATA,CODE}`) die aan een feature-branch hangen. Isolatie loopt via de **defaults** van de Variable Libraries (niet via een value set per developer) en het model/rapport worden per developer-workspace herbonden; een `normalize-bindings`-workflow zet die bindingen na de merge op `dev` weer terug naar de Dev-waarden. Het framework levert dit als `setup/NB_SETUP_DEVELOPER_WORKSPACES.ipynb` (modes `create`, `new_feature`, `switch_domain`, `bind`) en een sjabloon `templates/workspace-repo/.github/` voor de repo per workspace.
  **Bron:** `FMD/docs/adr/011-ontwikkelflow-repo-per-workspace.md` (ADR-011, Accepted, commit `574029d`); `FMD/setup/NB_SETUP_DEVELOPER_WORKSPACES.ipynb` (commit `5d59d6a`). **Status:** vastgesteld. Zie `03_technische_documentatie/09_cicd-en-deployment.md` en `03_technische_documentatie/14_ontwikkelproces.md` voor de volledige uitwerking.

  **Bron:** `FMD/docs/adr/006-promotie-via-fabric-cicd.md`, sectie "Geldt in beide gevallen"; herhaald in `bronnen/chats-ruw/2026-09-16_fmd-implementatiekeuzes-en-gevolgen_bijlage-beslisdocument.md` §5.4. **Status:** vastgesteld.
  **Correctie (2026-09-28, reden: Microsoft Learn bijgewerkt):** shortcuts gaan wél mee. Ze staan in `shortcuts.metadata.json` en worden door git en Deployment Pipelines gesynchroniseerd (GA). Voor FMD (Gold → Silver in een andere workspace) krijgt de doelstage dus de Dev-shortcuts, zodat `NB_CREATE_SHORTCUTS` na de promotie nog steeds nodig is. Een eigenschap van een shortcut kan aan een Variable Library-variabele gekoppeld worden, maar alleen via de portal. **Bron:** Microsoft Learn, *Lakehouse git integration and deployment pipelines* (2026-08-04) en *Assign variables to shortcuts*. **Status:** vastgesteld (Learn); het gedrag in FMD is een aanname, te testen in `testplan-trial.md` T-E04.

## Samenvattend antwoord op de `Promp.txt`-claim

De letterlijke claim is **geen vastgestelde koers**, maar een momentopname van het meest recente advies in één specifieke chat (`2026-09-16_medaillon-architectuur-deployment-en-git-integratie.md`), die op drie punten aantoonbaar afwijkt van wat elders formeel is vastgelegd:

1. **fabric-cicd als promotiemechanisme:** ADR-006 staat op *Proposed*, niet Accepted — expliciet omdat er al werkende Deployment-Pipeline-automatisering bestaat en een eerdere fabric-cicd-pilot al is teruggedraaid.
2. **"Voorkeur voor Azure DevOps":** ADR-007 (Accepted) kiest juist expliciet vóór een eigen GitHub-organisatie en verwerpt Azure DevOps.
3. **Het concept-beslisdocument zelf** noemt Deployment Pipelines, niet fabric-cicd, als Bitmetric-default voor promotie.

De technische details in de claim (config.yml/parameter.yml, dacpac + idempotente seed-scripts, approval gates, Key Vault-variable groups) zíjn wel ergens in de bronnen uitgewerkt — maar als verkennend ontwerp in een chat, niet als bekrachtigd besluit.

**Consequentie voor fase 2 (beslisdocument):** dit wordt een aparte, expliciete beslissing (`B-CICD-01` of vergelijkbaar) met Deployment Pipelines als voorlopige Bitmetric-default (conform het concept-beslisdocument en de praktijk in `NB_UTILITIES_SETUP_FMD`), en fabric-cicd als bewust opengelaten alternatief — precies zoals ADR-006 het zelf voorschrijft: pas sluiten na een fabric-cicd-proef + telling van de handmatige naloopstappen bij Deployment Pipelines.
