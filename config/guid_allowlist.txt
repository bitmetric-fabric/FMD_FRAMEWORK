# GUID's die bewust in src/, setup/ of wiki/ staan zonder in de vervang-tabel
# (config/item_config.yaml, config/item_deployment*.json) voor te komen.
#
# Formaat:  <guid> — <reden>
# Een regel zonder reden laat de guard falen. Dat is opzet: afwijken moet een
# zichtbare, beargumenteerde handeling zijn.
#
# Zie docs/adr/009-guid-guard.md.
#
# Voorbeeld:
# 11111111-2222-3333-4444-555555555555 — voorbeeld-GUID in wiki/LoadGroup_Scheduling.md, geen echte verwijzing

00000000-0000-0000-0000-000000000001 — sentinel-connectie: de rij in integration.Connection die 'geen externe connectie' betekent, gezet door sp_UpsertConnection in NB_SETUP_FMD. Geen verwijzing naar een Fabric-item, dus niet te mappen.

b9ad046b-6fcc-97ef-4b92-e4f1229b91e5 - logicalId van src/NB_FMD_CUSTOM_DQ_CLEANSING.Notebook. Dat notebook staat in src/ maar in geen enkele item_deployment*.json, dus het wordt nooit gedeployed en er is niets om het aan te mappen. Zijn tegenhanger NB_FMD_CUSTOM_NOTEBOOK_TEMPLATE is wel geregistreerd; mogelijk is dit een omissie. Registreren zou een nieuw item bij elke klant uitrollen, dus dat is een besluit, geen reparatie.

d18305e6-f633-4506-982c-53ee1c9dff16 — PLACEHOLDER connection op PL_FMD_LDZ_COPY_FROM_ADF (externalReferences.connection). De Bitmetric-tenant heeft geen Azure Data Factory, en create_or_get_fmd_connection() kan die connection-type niet automatisch aanmaken. De eerder gebruikte placeholder (CON_FMD_ADF_PIPELINES, 02e107b8) staat wel in item_config.yaml en werd dus door deploy_item() vervangen door een lege/foutieve waarde zodra de echte connection ontbrak, wat de deploy-import liet falen. Deze GUID staat bewust buiten de vervang-tabel zodat de import weer slaagt; de pipeline zelf faalt at runtime totdat iemand hem handmatig naar een echte ADF-connection wijst (zie de description op die activity).
